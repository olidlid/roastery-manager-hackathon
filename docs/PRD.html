01 Overview

What the system is, who runs their day through it, and where it stands today.

Roastery Manager Pro is a web application that runs the full production lifecycle of a coffee roastery: green coffee arrives and is logged into inventory, a roasting plan converts green stock into roasted batches on a specific machine, packing turns bulk roasted coffee into sellable bagged sizes, and sales staff take orders that a production leader approves before dispatch. Barcode scanning ties the physical floor — bags, lots, machines — to the records in the system.

It is built and used by one team today, with a second, independent deployment planned for a client (see Risks). The system is live in daily production use, not a prototype: roasterymanagerv2.vercel.app.

Primary users

Roasters, packing team, sales agents, production leaders, and admins — six roles in total, see §4.

Core loop

Green bean → roast batch → bulk roasted coffee → packed coffee → dispatch, with inventory decremented at each step.

Platform

Responsive web app, plus a lightweight companion Android app for leader approvals.

Data

Single shared Supabase project — every device and browser reads and writes the same live data, no per-device setup.

02 Problem & context

Why a roastery needs this instead of a spreadsheet.

A roastery's production chain has several handoffs — buying green coffee, roasting it on one of several machines, packing it into different bag sizes, and dispatching it to customers — and each handoff is a place stock can be miscounted, a batch can be mislabeled, or an order can go out without approval. Spreadsheets and paper logs don't enforce any of that, and don't give different roles (a roaster on the floor vs. a sales agent vs. an owner) a view scoped to what they actually need to see or touch.

The system replaces that with one shared record: inventory quantities move automatically as batches are logged and orders are packed, barcode labels make each roast batch and packed lot scannable instead of hand-written, and a role/permission model means a Packing Team account simply doesn't have a delete button to worry about.

03 Goals & non-goals

Accurate, live inventory

Green, bulk-roasted, and packed stock levels reflect reality at every step, without manual reconciliation.

Traceability

Every roasted batch and packed lot is scannable and attributable to a machine, a date, and (in V2) a specific green coffee lot.

Role-appropriate access

Each of the six roles sees only the sections and actions relevant to their job.

Runs anywhere, in two languages

Same data on any device, full English/Arabic support with RTL layout, no installation for the main app.

Non-goals

  • Not an accounting system — it tracks production and stock movement, not general ledger bookkeeping.
  • Not a B2B customer self-service portal (deferred to V3, see §11).
  • Not a point-of-sale system for walk-in retail.
  • Not multi-tenant — each deployment (this sandbox, and the future client instance) is its own isolated Supabase project.

Permissions gate the interface, not the database — Supabase row-level security is coarse (table-level), so the granular ~40-key model is enforced client-side. See §7 for the security implication of that.

A day in each role's life

  • Roaster — scans a green coffee or machine barcode to open the quick-log form, records a roast batch, moves on.
  • Packing Team — sees which sales requests need bags prepared, packs bulk roasted coffee into sized units, prints lot labels.
  • Sales Agent — enters a customer order as a request; the order carries their name automatically.
  • Production Leader — approves or rejects pending sales requests, including from the standalone Leader companion app on their phone.
  • Admin / Developer — manages users, roles, translations, and system settings; Developer additionally gets debug tooling.

05 Feature scope

Shipped functionality, organized by the module a user would open it from.

Dashboard

Landing view for every role. Surfaces notification badges for items awaiting the current user's action — pending sales approvals, pending roasting plans — on both the sidebar and the relevant section tabs.

Green Coffee Inventory

  • Stock table (alphabetically sorted) with quantity, origin, and per-item barcode generation for scan-driven roast logging.
  • Arrival / intake recording, matched to a specific green coffee record by its foreign key — not by text-matching the name — to prevent duplicate-stock bugs when two lots share a similar name.
  • Barcode label printing with selectable label/paper size (A4 multi-up, Letter, and dedicated sticker-roll sizes including 50×25 mm), tuned per size so the printed barcode stays within reliable scanner range.

Roasting

  • Roasting plans (what to roast, on which machine) and roast batches (the actual execution against a plan), with role-gated approval.
  • Blend recipes, combining multiple green coffees into a named blend that can itself be roasted.
  • Roasting log sticker: a scannable 50×25 mm barcode label per batch, with coffee name / machine / coffee code shown underneath per a configurable layout (§5, Settings).

Packing

  • Converts bulk roasted coffee into packed units at configured packaging sizes.
  • "Ready to Pack" view surfaces lot codes as scannable badges, tracked through production_lots.
  • Packed coffee lot barcode label (50×25 mm): batch/lot code, coffee name, production/expiry dates, and machine name, each independently toggleable in Settings.
  • Packed Coffee Stock table redesigned for row density — one row per coffee, two-row header — so a full inventory fits on screen without excess scrolling.

Sales & Dispatch

  • Customer management, sales agents, and request orders (a sales agent's order, itemized).
  • Approval workflow: a request moves to Pending Approval and a Production Leader approves or rejects it — from the main app or the standalone Leader companion app.
  • Dispatch confirmation and waybill/print output for approved, fulfilled orders.

Reports

Chart-based production and sales reporting. In progress — flagged in §9 as needing further work on data binding and date filtering before V2's AI phase builds on top of it.

Settings

  • Account — self-service password change for any logged-in user.
  • Users & Roles — user management, custom role creation with the full ~40-key permission matrix.
  • Production → Label Layout — two independent checklists controlling which fields print on the roasting log sticker and the packed coffee sticker respectively (the barcode itself always prints; only the surrounding text is optional).
  • Translations — import/export EN/AR strings via spreadsheet for non-technical editing.
  • Debug tools — Developer-role only; includes a mock-database reset utility.

Companion surfaces

Leader app

Minimal standalone page (also packaged as an Android app via Capacitor) that lists pending sales requests for one-tap approve/reject, for a leader who doesn't need the full system.

06 Cross-cutting requirements

Constraints that apply across every module, not features of any one of them.

Internationalization

Every user-facing string ships in English and Arabic. Arabic triggers a full right-to-left layout, including sidebar mirroring — this is a hard requirement, not a stretch goal, since Arabic-speaking staff use the app daily.

Theming

Dark and light mode, driven entirely by CSS custom properties so the two themes can't drift out of sync feature-by-feature.

Barcode & label printing

Scannability is a first-class requirement, not a visual nice-to-have: barcode height, module width, and print-driver page sizing have each been a real production defect at least once (a barcode that looks correct on screen but doesn't scan off the printed sticker). The standard is a 50×25 mm physical label across roasting, packing, and green coffee stickers, with print CSS that scales the barcode to fill that label without distorting its aspect ratio.

Authentication & permissions

  • Email/password and Google OAuth sign-in.
  • Self-service password change plus an admin-triggered reset that doesn't require the target user to click an email link, backed by a Supabase Edge Function running under a service-role key that the browser never sees.
  • Permission checks are enforced in the UI layer; the database's own row-level security is table-level only. This is an accepted trade-off today (see §12) rather than an oversight.

Deployment model

No build step for the main app — every script is a plain <script> tag loaded directly by the browser, in a fixed dependency order, sharing one global scope. Vercel auto-deploys from the main branch. This keeps the barrier to shipping a fix low, at the cost of not having module isolation or a bundler-enforced dependency graph — a deliberate trade documented in full in REFACTORING.md.

07 System architecture

What it's built with, and how the pieces load.

LayerChoice
FrontendHTML, CSS, vanilla JavaScript — no framework, no bundler
BackendSupabase (PostgreSQL + Auth + Edge Functions)
HostingVercel, auto-deploy on push to main
Barcode renderingJsBarcode (CODE128), rendered client-side and at print time
ChartsChart.js
IconsLucide
Companion mobile appCapacitor-wrapped build of the Leader page, targeting Android

The nine main-app scripts load in a fixed order — db → auth → greenbean → roasting → packing → sales → settings → tracking → app — each in the same global scope, so anything defined earlier is available to everything after it. There is intentionally no ES module system: the plain-script approach was chosen specifically to avoid rewriting ~80 inline event handlers and ~25 mutable global state variables during the V1 modularization.

Full Supabase mode. The app always talks to one live Supabase project — there's no local/demo mode toggle for end users. A legacy mock-data layer still exists underneath (seed data + a Developer-only reset tool) but is not a real operating mode.

08 Data model

Twenty tables in production. The ones a reader needs to know to understand the product:

TablePurpose
profiles / custom_rolesUsers and the permission sets their role grants.
green_coffee / green_coffee_intakeGreen bean catalog and each arrival/intake event.
blend_recipes / blend_ingredientsNamed blends composed of multiple green coffees.
machinesRoasting equipment a batch can be assigned to.
roasting_plans / roast_batchesPlanned production runs and their executed batches.
bulk_roasted_coffee / waste_inventoryRoasted output awaiting packing, and roasting loss.
packaging_sizes / packed_coffee / packing_recordsBag sizes, resulting packed stock, and the packing events that created it.
customers / sales_agents / request_orders / request_order_itemsThe sales & dispatch workflow.
company_settingsSingle-row configuration: branding, and the label-layout checklist from §5.

Two additional tables — green_coffee_lots and packed_coffee_lots — already exist as shadow schema, created ahead of need during V1 specifically to unblock V2 Phase 1 (§11) without a further migration.

Schema-drift discipline. database/supabase_schema.sql is the single source of truth and must be updated in the same change as any live schema edit — six production bugs in one week were traced directly to this file falling out of sync with the real database. Any schema PR that doesn't touch this file alongside the code change should be treated as incomplete.

09 Current status

An honest read on what's solid, what's still being shaken out, and what's known debt.

Working in daily production use

Auth (email/password + Google), role-based access across six roles, dashboard, green coffee inventory, roasting plans & batches, packing, sales requests & dispatch approval, dark/light theme, EN/AR i18n, barcode scan-to-log, customer management.

Needs more testing or completion

  • Full end-to-end walkthrough of Green Bean → Roasting → Packing → Sales as one continuous flow.
  • Reports module: chart data binding and date filtering.
  • Print output coverage across all document types (requests, dispatch, waybill, labels).
  • Mobile responsiveness of the main app (the Leader companion app is mobile-first by design; the main app is not yet).

Known technical debt

  • Dead if (isMockMode) branches remain throughout the codebase, kept alive only by the Developer debug reset tool.
  • A stale, pre-refactor copy of the app (dist/js/app.js) sits in the Android build source but isn't actually referenced by the build — safe to delete, not yet done.
  • A handful of leftover scaffold files and folders from earlier refactor passes (empty module stubs, a GitHub Desktop tutorial folder) carry no functional risk but add noise.

10 Roadmap — V2

Two phases, scoped 2026-07-11. V2 ships into the current sandbox project — it is not part of what forks to the client deployment.

Phase 1 — FIFO lot tracking

Planned · foundation in place

Costing and freshness, driven by the same lot data: cost-of-goods should reflect what a specific batch of green coffee actually cost, and older stock should get used before newer stock sitting next to it.

  • Populate green_coffee_lots on every intake, one row per arrival batch, ordered by date.
  • Roast batch logic consumes the oldest lot first, decrementing it and recording which lot(s) a batch drew from.
  • Extend cost calculations to a lot-weighted cost instead of one flat green-coffee cost field.
  • Surface remaining lot age and quantity in the Green Bean inventory UI, so rotation is something staff can act on, not just a background computation.
  • Decide whether packed_coffee_lots needs the same treatment on the packing side — not yet confirmed with the business.

Phase 2 — AI: forecasting & report insights

Planned · blocked on Reports

Demand/stock forecasting from historical data, plus plain-language insight summaries alongside the existing Reports charts.

  • Explicitly sequenced after Phase 1 — no technical dependency, just priority order.
  • Blocked on the Reports module's own outstanding testing gaps (§9) and a separate set of Reports changes the business has in mind but hasn't finalized — building forecasting on an unstable Reports base would mean redoing it.

11 Out of scope

Work Order Not needed

Confirmed already covered by the existing Roasting Plans → Batches flow. No separate entity is being built unless a concrete gap surfaces later.

B2B customer portal Deferred to V3

Self-serve ordering or per-customer contract pricing — direction not yet chosen, and not needed for V2.

WhatsApp leader notifier Removed

Standalone Node service that nudged the leader on WhatsApp for a new pending approval. Never used in practice and not needed soon, so it was removed (2026-08-27) rather than kept as unused surface area. Independent of the core approval workflow either way — a leader still sees pending requests in-app or in the Leader companion page.

12 Risks & open questions

  • Client handover in flight. The plan is to fork this codebase onto the client's own Supabase and hosting accounts, while this team keeps access for future updates and continues V2 work on the current sandbox. Web hosting recommendation and domain are not yet finalized.
  • Client-readiness bar. Everything in this document should be read with an eye toward what a handed-off client needs: clear ownership of credentials, no hardcoded secrets a client can't rotate themselves, and documentation that doesn't assume this team is still in the room.
  • Client-side permission enforcement. Because Supabase RLS is table-level, the ~40-key permission model is only as strong as the JavaScript enforcing it. Acceptable for a trusted internal team; worth revisiting before any external/B2B surface (§11) is built on the same data.
  • Reports scope is unresolved. Business-side changes to Reports are known to be coming but haven't been specified — this is the one item actively blocking V2 Phase 2 from starting cleanly.
  • packed_coffee_lots decision. Whether packed-goods rotation/costing matters as much as green coffee lot tracking is an open question for Phase 1, not yet put to the business.

13 Glossary

Green coffee
Unroasted coffee beans, tracked from intake as raw inventory.
Roast batch
One execution of roasting a quantity of green coffee (or a blend) on a specific machine, on a specific date.
Bulk roasted coffee
Roasted output sitting between the roaster and packing — not yet portioned into sellable units.
Packed coffee
Roasted coffee portioned into a sized, sellable bag.
Lot / lot code
A scannable identifier tying a physical batch of stock (green or packed) back to its production record — the unit that V2's FIFO phase costs and rotates by.
Request order
A sales agent's order for a customer, pending Production Leader approval before it can be dispatched.
Dispatch
The confirmed handoff of an approved, packed order to the customer.
RLS
Row-level security — Postgres/Supabase's built-in access control, applied here at the table level rather than per-permission-key.
